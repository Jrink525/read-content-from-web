# 厂商工作流贴：N 种方法、自家命令、零测量

用于作者在自家公司、文中每条命令都是他家平台的产品、全文没有任何实验数据的方法类帖子。这类文章容易写成产品说明书，也容易被读成工具中立的评测。

## 骨架

1. 速览 6–8 条：先把作者的分类原样列出，再单独一条写全文真正的共同主张——通常是「把这项工作交给谁做」，而不是三选一。
2. 问题被放在了哪一层单独一节：作者把话题收窄到哪个具体动作，以及他选的贯穿例子为何合适（选边界情形，不是选能不能跑）。
3. 每种方法一节，四件事固定不变：从什么材料出发、怎么做、堵住哪类失败、作者自己给它划的边界。原文的方法对照表整表保留。
4. 一段把几种方法串在同一个例子上，写清流水线顺序（谁负责发现、谁负责锁住、谁负责扩边），不要并列成三个选项。
5. 工程门槛单独一节：原文一句话带过、但落地之前必须先有的那几件事（样本带版本、判分独立于生成者、改动可回滚）。
6. 可迁移原则 5–8 条，去掉厂商专有名词后仍然成立。
7. 局限第一条写「这是厂商工作流说明，不是效果证明」：零测量；命令属于作者雇主的平台，方法可迁移而命令不可照搬；再列厂商没描述的部分（样本怎么选、判分是否独立、改坏过的案例与回滚）。

## 规则

- 当文中每条命令都属于作者雇主的平台时，在来源块直接写明这层关系，别让页面被读成工具中立的评测。
- 作者没有讨论的评估弱点要自己补成推论并标明：同一模型既生成用例又判分时，结果只能当线索；写清新练者该怎么拆开（判分标准与请求生成分开写，定期人工抽检校准）。
- 平台命令原样保留，但每条后面跟一句「它实际做的是哪几件事」，这样读者不在该平台上也能拿走方法。
