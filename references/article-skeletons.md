# 写页面的骨架：按来源类型选

写完 claim map（SKILL.md 第 3 步）之后、动笔之前读这份。骨架选错，页面会变成目录复述；骨架选对了，同样的事实短一半。

## 通用规则

- **每节结论先行**：第一节第一句写该节可判定的结论，后面才是证据、引用与代码。自检：删掉该节最后一段，该节仍然成立。
- **每节只放一项设计决策**，紧接着写它堵住哪一类故障。两层意思塞一节，读者会只记住最后那层。
- **数字只写原文给的**；没给就写「原文未给」，不要估。
- 篇幅档位：单篇 5,000–7,000 汉字；多源 6,000–9,000；清洗后正文只有 10–15 K 字符的短教程 3,000–4,500；清洗后 4–6 K 字符的短 X Article 2,500–3,500；索引页（每步一段加链接、散文不足 3 K 字符）2,000–3,000。
- 短篇的增量放在「核对」「原文未答的问题」「原文没写的失效模式」，不复述章节凑长度。

## A. 多源工程长文（一篇 X 帖 + 若干博客/线程）

1. 开头用作者自己的钩子（具体场景或抱怨），不要用摘要开场。
2. 旧做法为什么不行。
3. 按阶段讲演化，一节一个来源，带日期。
4. 机制逐层展开。
5. 工程细节：状态机、挂起、并发栅栏、事件服务。
6. 语义层：小决策模型、建议权与决定权分离。
7. 真实运行数据。
8. 反直觉判断，四到六条。
9. 可迁移清单，五到八条。
10. 收尾用作者自己的框架。

## B. 单源工程博客

1. 开头放 6–8 条速览，每条带原文数字，让人不读全文也能拿到结论。
2. 问题定义：原文自己说的「旧做法为何不够」，尤其是它列举的失败模式，这是全文最值钱的部分。
3. 机制逐层展开：一层一节，每节写一项设计决策加它堵住的故障。
4. 结果：只写原文给过的数字；没给就写「原文未给」，不要估。
5. 可迁移原则 5–8 条，去掉厂商专有组件名后仍然成立。
6. 局限：列原文没回答的问题（规模、误报率、成本、对某云的依赖），标「原文未明确」；厂商自述的用量、token 对比与效果百分比单列一条，写明无第三方验证与测量方法。

## C. 代码为主的教学文（一篇文从零建出东西）

1. 速览 6–8 条，每条是一句可检验的结论，带原文的数字或命令。
2. 把原文的核心判断单独一节，写清它反对的常见误解。
3. 按原文步骤走：每步先给代码，再写每个参数在堵什么故障。
4. 原文自带的验收用例整段保留，说明它检验的是哪条链路。
5. 「原文代码的问题」编号列出，每条给原因和改法；教程代码通常缺异常处理、步数上限、进程清理。
6. 加固版：保持原工具签名，只补缺失的防护，并说明仍未解决什么。
7. 把每个环节映射到用户熟悉的真实产品（工具名、沙箱、checkpoint），让读者接上已有认知。
8. 局限：原文没测的规模、没给的数字、本机无法实跑的部分。

## D. 产品发布或功能更新

1. 速览 6–8 条，把「这次改了什么」写成可核对的事实：数量从 X 到 Y、新增哪几项、环境要求是什么。
2. 定位变化单独一节：产品从什么变成了什么，以及这个变化为什么决定后面所有设计。
3. 新内容逐项列表：每项写手法加适用场景，保留原文的分类学，不按自己的偏好重排。
4. 使用流程按步走：命令原样保留，每步写清产出物与需要用户确认的点。
5. 工程实现：技术栈、运行环境、许可分拆，这三项是读者的选型依据。
6. 可迁移设计原则 4–6 条，标明是自己的提炼而非原文结论。
7. 局限：未发布的功能、作者自测的效果、只是路线图的数字、本机未实跑的部分。

## E. 课程、视频系列或资源发布

1. 速览 4–6 条：几讲、总时长、面向谁、前置要求、配套材料。
2. 先立概念：作者对核心术语的定义原样引用，这类文章可迁移的通常只有这一段界定。
3. 每讲或每章一节，保留原文的主题清单，不合并、不重排、不在节末加评语。
4. 配套材料列成表格：书、视频、前作、可选短课，各写用途与获取方式，并保留价格或时长等原文数字。
5. 局限第一条写「这是课程发布文，没有结果表、没有训练曲线、没有可对照的准确率」，再列单模型、单数据集这类范围限制。

课程发布文最容易写成课程目录复述：把每讲的「涵盖」清单压成一句话会丢掉读者真正要判断的信息（先教什么、评估何时插入、哪些步骤被简化），宁可逐讲保留清单，也不要用概括换字数。

当页面是索引而非讲稿（每步一段说明加链接、散文不足 3 K 字符）时，写成 2,000–3,000 汉字：速览 6–7 条，每步一节写「原文说了什么 + 它堵住哪类故障」，原文的「步骤 / 训练器 / 需要准备什么」表整表保留，局限第一条写「这是课程索引页，不是方法论文：没有任何实验数据」。不要把每个链接标题展开成一段解释去凑字数，短而诚实的索引页就是交付物。

## F. 面试准备或问答文（一页编号小节 + 题库）

1. 速览 5–6 条，每条对应原文 Key takeaways 的一句可记住结论。
2. 逐节保留原文的机制描述与调用链，代码、JSON、配置片段原样保留；节号不必与原文一致，但顺序必须一致。
3. 把全文最容易混淆的一对概念单独用一节拆开（例如「统一接口」 vs 「能力等价」），这类文章的骨架就在这一节。
4. 问答部分按原文编号压成一问一答要点，不合并问题、不删小问题；文末那段「标准答案」整段保留并附中译。
5. 局限第一条写「这是面试口径，不是实现」：无代码、无测量、只有示意片段；再把原文点名但没展开的机制（熔断阈值、重试预算、幂等判断）逐项列为缺失，不要替它补全。
6. 目录页数据（发布时间、阅读时长、浏览与点赞数）只写进来源块当作材料性质，不当成内容质量证据。

## G. 概念解释文（为什么存在某个东西、两个阶段或方法差在哪）

1. 速览 5–8 条，每条是一个能独立记住的结论。
2. 用原文的具体对比例子开场，先给作者的解释，再展开。
3. 术语在第一次用到的地方定义，不单开名词表。
4. 把最容易混淆的两个概念按 5 个维度并排（目标 / 数据 / 信号 / 成本 / 改动幅度）。
5. 每种方法一节：老师是谁、数据长什么样、信号落在哪些 token 上、它修不掉什么。
6. 第一节「我的补充」，把框架展开成可操作判断，并标明不是原文内容。
7. 收尾列原文没展开的问题，标「原文未涉及」。

## H. 观点或立场文（一个论证加一串未解问题，无机制无数据）

1. 速览 4–6 条，每条是作者的一句立场，不掺自己的评价。
2. 主线单独一节：作者认为哪一类问题决定成败，以及他为什么把它归到工程问题而非模型能力问题。
3. 按原文自己的问题分类逐节展开，每类只写它点名的缺口与现状，不替作者补方案。
4. 把全文判断力最强的句子单独引用（例如善意坚持与恶意行为不可区分），再写它否定了哪种检测做法。
5. 收尾保留作者对读者的判断，并标明这是价值判断而非可检验结论。
6. 局限第一条写「这是立场文，不是方案」：无架构图、无接口、无选型对比；随后逐项列原文提出但没有推进的问题。

## I. 架构设计文档（模块、设计理由、小规模实验、开放问题）

1. 速览 6–8 条，每条带原文数字或原文自己的限定条件，并在来源块里写明「这是设计文档，不是现状说明」。
2. 问题定义单独一节：作者把瓶颈归到哪（通常是人的注意力或系统结构，不是模型能力），以及他反对的默认假设是什么。
3. 逐模块一节，模块号沿用原文；每节写三样：借自哪个经典系统概念、它堵住哪类故障、作者给它划的边界。
4. 实验整表保留，并连着代价读：主结果旁边同时给 token、成本、以及「去掉某个机制要多付多少」，这张对照才是读者真正要判断的东西。
5. 把模块映射回经典系统概念单独一节（调度器、进程、缓存层级、看门狗），标明是自己的推论：这层映射是读者最难自己补上的。
6. 原文的未解问题整节保留，逐条标它是工程缺口还是能力缺口，不替作者补方案。
7. 局限第一条写负载规模与合成性质，再列作者自己承认的实现落差（默认未开、原型非产品），这两类比外部批评更有用。

## J. 厂商工作流贴（N 方法、自家命令、零测量）

用 `references/vendor-workflow-post.md`。要点：保留它的分类学，命令原样保留并标注环境前提，页面开头就写明这是厂商方法而非中立评测。

## K. 中文原文

原文过半是汉字（X Article、公众号、中文博客）：不翻译、不标译文，引文用「」照抄原文的数字写法。规则与核对脚本见 `references/chinese-source.md`。
